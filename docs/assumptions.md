# Modeling assumptions

This project is a synthetic data and rule-detection prototype. It is meant to exercise relational integrity, anomaly labels, traceability, and repeatable output. It is not a hydraulic solver or a plant control system.

## Why the prototype is structured this way

- **Stable equipment IDs:** IDs such as `PUMP-001` make joins readable and repeatable. IDs do not encode changing properties such as location or status.
- **Facility ownership:** every pump, tank, valve, pipe, and sensor belongs to one facility so reports can be grouped by site and foreign keys can be checked.
- **Connected equipment paths:** pipes connect equipment nodes in a cycle within each facility. This gives graph connectivity for initial exercises, but does not represent a detailed engineered layout.
- **One sensor per equipment item:** sensor coverage is intentionally simple and creates a useful starting dataset. A richer model should add multiple sensors per asset and sensors mounted on pipes.
- **Synthetic nominal readings:** the prototype uses fixed nominal values by metric with seeded Gaussian noise. This makes the data reproducible and easy to inspect; real facilities would need operating ranges derived from engineering records.
- **Fault signal multipliers:** four deterministic scenarios alter readings and write labels to a separate ground-truth file. These patterns are useful for validating a pipeline but are only proxies for actual physical fault signatures.
- **Rule-based detection:** the current alarm rule raises an alarm when a reading differs from its fixed nominal value by more than 20%. This is transparent and easy to evaluate, but does not yet account for operating mode, asset-specific curves, or cross-sensor evidence.
- **Flow residual:** the current residual is `observed flow - 100 m3/h`. It is a simple derived metric for exercising reconciliation checks, not a network-wide mass balance.
- **Negative fixtures kept separate:** invalid references and inconsistent conditions are supplied as explicit examples so they can be fed to validators without contaminating the clean baseline exports.
- **Fixed UTC start and random seed:** identical command-line arguments produce identical timestamps, noise, labels, and file hashes, making changes reviewable.
- **No external dataset:** the data is synthetic, avoiding licensing and confidentiality questions. No public process data is claimed as a source.

## Engineering upgrades needed for stronger physical realism

Represent actual inlet/outlet connections, use pump curves and valve openings, derive tank level from inflow and outflow over a time step, and calculate mass balance across network nodes. Inject faults into those underlying process quantities before producing sensor readings. Then evaluate detection precision and recall using the separately stored scenario labels.

## One-line prototype caveats

- The line solver defines outlet flow as inlet flow minus modeled leak flow. Therefore `q_in - q_out - q_leak` being near zero checks bookkeeping, not physical realism. Tank updates use the same solved values.
- A leak is most directly visible as inlet/outlet flow disagreement, requiring flow sensors at both ends. A blockage pressure increase applies upstream of the restriction; downstream pressure can decrease. The current full generator does not model sensor position, so it cannot support a location-aware pressure detector.
- The line prototype includes a leak-coefficient sweep and reports process signal changes. It has no measurement noise model, so a minimum detectable leak threshold cannot be claimed until noise and sensor placement are represented.
- The 2% noise floor in the sensitivity report is only an illustrative planning value. The report labels the smallest parameter in its sweep that exceeds this assumed signal cutoff; it is not an empirically established `TAU` until sensor noise is measured.
- For paired inlet/outlet flow, channel noise is treated as independent and the differential standard deviation is √2 times single-channel noise. The percentage is applied to nominal flow, not to the near-zero baseline difference. Actual sensor errors may be correlated or biased, so measured noise data should replace this assumption.
- Pump degradation is modeled as a 10% reduction in shutoff head, blockage as a 3x pipe resistance, and the partial valve as 65% opening. Their signal directions are checks against this model's assumptions, not universal fault signatures.
- The solver finds a steady operating point at each one-minute step. It does not simulate transients, water hammer, fluid compressibility, or pipe elasticity.
- `src/network_expansion.py` is the sole supported generator. Its target topology is 3 facilities, 20 pumps, 30 tanks, and 60 valves, with pumps distributed 7/7/6 and 20 valves per facility. Series valve-train sizes vary from two to four per pump line. Every facility graph is checked for connectivity. Each run's config records the seed, per-metric relative noise standard deviations, base model settings, and detectability sigma. Fault parameters and labels are kept in ground truth, separate from telemetry and run config.
- Network sensor placement is represented by `entity_id`, `node_id` or `pipe_id`, and `position`. Flow sensors sit at each line inlet/outlet; pressure taps cover pump discharge, valve-train outlet, and pipe outlet. Two to four series valves and multiple pipe segments are explicit asset rows; their resistances are aggregated for the line solver. The 8 buffer tanks per facility are reserve assets held at configured initial levels with no simulated flow; only each facility's shared source and destination levels evolve in this prototype.
- Equipment events are emitted from state snapshot differences between baseline and faulted runs and include a restore transition at the run end. The sensor-fault scenario freezes only the inlet flow reading; its true process values stay at baseline and its ground-truth process-fault flag is false.
- The expansion's true network residual is calculated from line leak flow and the shared tank storage change. Since storage updates use the same solved line flows, it is a reconciliation check, not independent validation of hydraulic realism. The measured residual adds generated flow-sensor noise. At the default target scale, its p95 is about 17.5 m3/h. The validator limit is a two-sided 99% Gaussian envelope propagated from independent flow-sensor noise, not an empirical residual sigma or a 3σ limit; the measured fault-free exceedance rate is 6/1,049 steps (0.57%). The injected violation is three times the limit. Paired inlet/outlet flow is the stronger leak signal under these assumptions.
- The default 100,000-row target is reached exactly by allocating whole samples across runs (69–71 one-minute samples); paired fault runs retain the same horizon as their baseline. Noise assumptions are synthetic and must not be described as measured plant performance.
- The flow-balance tolerance is a two-sided 99% Gaussian envelope propagated from the configured independent inlet/outlet flow-sensor noise and summed across a facility. It is not a measured residual standard deviation or a 3σ residual threshold. The validation summary reports the observed exceedance rate on fault-free runs, and the injected fixture is three times the tolerance.
- The short run windows are a deliberate scale choice: all 130 default sensors emit each sample while the telemetry total stays at 100,000. They cover about an hour, have no diurnal demand pattern, and do not spread starts across morning/night. Baseline shared tank levels move by about half a metre in that window. Pump degradation is modeled as an immediate 10% shutoff-head reduction, not gradual daily wear; its mean discharge-pressure effect is about -24.5 kPa over the short window.
- Window alarms and the `detectable` label share the 3σ threshold and run-specific sample count. Alarms use measured effects; process-fault `detectable` uses truth effects (sensor-fault detectability uses the measured effect). `alarm_detected` records the emitted window alarm. The current alarm path only evaluates labeled fault windows, so it does not yet provide independent precision/recall from a scan of clean telemetry.
